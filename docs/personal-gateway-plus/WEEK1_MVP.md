# Personal Gateway Plus：一周可用初版冲刺计划

> 历史冲刺计划：其中 Android 任务自 2026-08-18 起作废，当前开发和验收只覆盖 Web 与服务端。

> 冲刺周期：2026-08-04 ～ 2026-08-11  
> 团队规模：5 人  
> 目标：在本地环境交付一个可以真实调用、可以演示故障切换的初版  
> 明确不包含：服务器购买、域名、HTTPS 证书和线上部署

## 1. 一周后的交付效果

演示者可以在 Web 页面完成以下闭环：

1. 查看内置的主流模型、供应商价格和活动信息，并看到来源及更新时间。
2. 添加两个 OpenAI Chat Completions 兼容上游，API Key 不在页面回显。
3. 创建一个 API 分组，把两个上游加入分组并调整优先顺序。
4. 在“调用测试”页面选择分组并发送真实问题。
5. 第一上游正常时直接返回结果。
6. 第一上游超时、返回 429 或 5xx 时，自动切换到第二上游。
7. 页面显示最终使用的上游以及简化的路由尝试记录。
8. 现有 Android 应用至少能读取本地后端的模型、价格和活动；如果联调顺利，再通过分组调用网关。

这八项全部完成即可称为“可用初版”。初版只承诺单机、单用户、非流式调用。

## 2. 必须严格控制的范围

### 本周必须完成（P0）

- 本地可运行的后端服务和 SQLite 数据库。
- 供应商和上游 API 的新增、编辑、启停与删除。
- API Key 加密保存或使用受控密钥存储，接口永不返回明文。
- 模型、价格、活动的内置种子数据和查询接口。
- API 分组、组成员、启停和优先级排序。
- OpenAI Chat Completions 非流式兼容入口。
- 超时、连接失败、429、5xx 的顺序故障切换。
- 400/422 参数错误不切换，避免无意义请求。
- 最多尝试次数和整次请求总超时，防止无限重试。
- 最小路由记录：请求 ID、尝试顺序、上游、结果、错误类型、耗时。
- Web 管理端和调用测试页面。
- 自动化核心测试、演示数据、使用说明和 3～5 分钟演示流程。

### 有余力再完成（P1）

- Android 通过 API 分组发起真实网关调用。
- 简单的上游连通性测试按钮。
- 最近 20 条路由记录页面。
- 请求 Token 和估算费用展示。
- 价格、活动的简单后台编辑表单。

### 本周明确延期（P2）

- 登录、注册、多用户和复杂权限。
- SSE 流式响应与流式中途故障处理。
- 熔断器、主动健康检查和 Half-open 恢复。
- 自动抓取价格、自动发现优惠和汇率换算。
- 历史价格趋势、预算、限额和复杂用量仪表盘。
- 非 OpenAI 协议供应商适配。
- Responses、Embeddings、图片、语音等其他接口。
- Docker、CI/CD、云服务器、监控告警和备份恢复。
- 移动端完整管理后台。

任何 P2 需求本周都不能挤占 P0 时间。

## 3. 初版最小技术边界

### 本地结构

```text
TS/
├─ app/                 # 已有 Android 客户端
├─ server/              # 本地后端与网关
├─ web/                 # 本地 Web 管理端
├─ contracts/
│  └─ openapi.yaml      # 前后端共同接口
└─ docs/
```

后端框架必须选择团队最熟悉、当天能启动的方案，不为“技术先进”更换陌生框架。数据库统一使用 SQLite，避免本周引入额外服务。

### 最小数据模型

- `Provider`：供应商名称、官网和启用状态。
- `UpstreamEndpoint`：供应商、显示名称、Base URL、加密 API Key、默认模型、启用状态。
- `ModelCatalogEntry`：规范模型名称、供应商、输入/输出价格、币种、来源、更新时间。
- `Promotion`：标题、供应商、说明、来源、起止时间。
- `ApiGroup`：名称、用于调用的唯一 `routeKey`、启用状态。
- `ApiGroupMember`：分组、上游、上游模型名、优先级、启用状态。
- `RouteAttempt`：请求 ID、顺序、上游、状态、错误类别、耗时。

### 最小调用协议

- 对外入口：`POST /v1/chat/completions`。
- 请求保持 OpenAI Chat Completions 格式。
- 请求中的 `model` 填分组的 `routeKey`，每个组成员再映射到自己的真实上游模型。
- 初版只接受 `stream=false`；收到 `stream=true` 时返回明确的“不支持”错误。
- 成功响应保持 OpenAI 兼容结构，并额外通过响应头返回请求 ID 和最终上游名称。

这种设计可以在不增加自定义请求字段的情况下实现分组路由，后续也容易接入现有 OpenAI 客户端。

## 4. 五人一周分工

### A：技术负责人兼接口整合

适合：水平最高、能快速解决跨模块问题的成员。

本周任务：

- A1：2 小时内确定后端/Web 技术栈和本地启动方式。
- A2：创建 `server/`、`contracts/openapi.yaml`，定义所有 P0 接口和统一错误格式。
- A3：实现后端基础结构、SQLite 初始化、配置加载、请求 ID 和全局错误处理。
- A4：确定 API Key 加密方式，检查日志脱敏和 `.gitignore`。
- A5：每天两次合并和集成，解决 B/C/D/E 的接口冲突。
- A6：冻结最终版本、编写一键本地启动说明和已知限制。

验收：全新电脑按文档可以启动后端和 Web；接口契约与实际响应一致；仓库中没有真实密钥。

工作量控制：A 不负责大量业务页面，也不亲自包办路由和数据模块，主要保证其他四个人能并行。

### B：网关与自动路由

适合：后端能力较强，熟悉 HTTP、超时和异常处理的成员。

本周任务：

- B1：实现单上游非流式 Chat Completions 转发。
- B2：根据 `routeKey` 查询分组成员，并按优先级生成候选列表。
- B3：实现连接失败、连接/读取超时、429、5xx 自动切换。
- B4：实现 400/422 不切换，以及最大 3 次尝试和整次请求总超时。
- B5：记录每次 RouteAttempt，并在响应头返回请求 ID 和最终上游。
- B6：使用 E 的模拟上游完成正常、第一上游失败、全部失败测试。

验收：关闭或模拟第一上游故障后，请求稳定切到第二上游；第一上游正常时不访问第二上游；全部失败时返回可理解错误。

明确不做：流式、熔断、主动健康检查、负载均衡、最低价自动选路。

### C：供应商、价格、活动和分组数据

适合：中级后端或数据库较熟悉的成员。

本周任务：

- C1：建立 P0 数据表和迁移/初始化脚本。
- C2：实现 Provider、UpstreamEndpoint CRUD，API Key 写入时加密、读取时脱敏。
- C3：实现 ApiGroup 和 ApiGroupMember CRUD、批量排序与启停。
- C4：准备 3～5 个供应商、8～12 个主流模型的价格种子数据。
- C5：准备 3～5 条活动/价格调整演示数据，全部标记来源和更新时间。
- C6：实现模型、价格、活动查询接口，协助 B 提供稳定的候选查询。

验收：重启后数据仍存在；同一分组排序结果稳定；价格缺失不显示成 0；活动可以判断是否过期；接口不返回明文 API Key。

明确不做：自动网页抓取、价格历史、汇率、复杂活动规则和用量聚合。

### D：Web 管理端

适合：前端能力较强或熟悉 React/Vue 等框架的成员。

本周任务：

- D1：创建 `web/`，完成基础布局、API 客户端、错误提示和加载状态。
- D2：完成“模型价格”和“活动信息”两个展示页面。
- D3：完成“供应商/API 管理”页面，支持增删改、启停和密钥输入。
- D4：完成“API 分组”页面，支持创建分组、加入成员和调整优先级。
- D5：完成“调用测试”页面，输入问题后显示答案、最终上游和请求 ID。
- D6：如果时间允许，显示最近路由尝试记录；否则在调用结果中直接展示。

验收：用户不需要修改数据库或配置文件即可完成完整演示；刷新页面后配置仍存在；错误状态不会出现空白页面。

为了保证进度，优先使用“上移/下移”按钮完成排序，拖拽排序降为 P1。不要把时间消耗在复杂动画和视觉装修上。

### E：Android、模拟上游、测试和演示

适合：初级到中级成员，熟悉现有 Android 项目或测试工作。

本周任务：

- E1：第一天建立模拟上游，可稳定返回正常、超时、429 和 500。
- E2：整理核心验收用例并帮助 B 自动化故障切换测试。
- E3：将 Android 的供应商、模型和活动请求地址切到本地后端并完成回归。
- E4：如果 D4/B2 在第四天前稳定，再接入 Android 分组调用；否则保留现有 Android 对话，不阻塞 Web MVP。
- E5：执行整体验收，准备不含真实密钥的演示数据。
- E6：录制或排练 3～5 分钟演示，整理提交包和问题说明。

验收：模型价格和活动在 Android 正常展示；模拟故障可重复；关键路径有测试记录；最终演示不依赖临时手工改代码。

## 6. 每日协作规则

- 每天上午进行 15 分钟同步：昨天结果、今天目标、当前阻塞。
- 每天中午和晚上由 A 各合并一次，避免最后一天才集成。
- 接口变化必须先修改 OpenAPI 并通知相关人员，不能只在聊天中说明。
- 每人每天至少提交一个可运行结果，不以“完成了大部分”作为状态。
- 遇到阻塞超过 1 小时立即求助，不独自研究半天。
- PR 尽量控制在半天到一天的工作量，禁止三天后提交一个超大 PR。
- 使用假的演示 Key 或个人临时 Key，提交前检查 Git 历史和日志。

## 7. 初版验收清单

- [ ] README 写明环境要求和启动命令。
- [ ] 不需要手动修改数据库才能演示。

### 数据展示

- [ ] 能看到输入/输出价格、币种、来源和更新时间。

### 交付

- [ ] 核心测试通过。

- [ ] 已知限制明确写出：单用户、本地运行、非流式、人工价格数据。

## 8. 演示流程建议

1. 打开价格页面，展示不同供应商模型价格及来源。
2. 打开活动页面，展示有效期和来源链接。
3. 添加两个演示上游，其中第一上游使用可控制故障的模拟服务。
4. 创建分组 `demo-route`，第一成员为模拟上游，第二成员为真实可用上游。
5. 首次请求让第一上游正常返回，说明遵循人工排序。
6. 将第一上游切换为 500 或超时，再次发送相同问题。
7. 展示系统自动使用第二上游，并打开路由记录说明切换原因。
8. 最后展示 Android 读取同一份模型价格和活动数据。

这套流程能在 3～5 分钟内直接体现“价格聚合、活动信息、API 分组、人工优先级、故障自动路由”五个项目核心价值。

## 9. 一周内的成功标准

成功不等于完成完整规划，而是交付一个边界清楚、可以稳定重复演示的初版。只要本地 Web 能配置两个上游、创建有序分组、通过 OpenAI 兼容入口真实调用，并在第一上游故障时自动切换，同时展示模型价格和活动信息，本次一周冲刺就达到目标。
