| 项 | 内容 |
|---|---|
| 交付对象 | B（网关与自动路由） |

---

## 0. 这份清单测什么

验证 B 网关的**顺序故障切换**是否达到 WEEK1_MVP §7 验收标准：

- 第一上游正常 → 只走第一，不碰第二
- 第一上游 **超时 / 429 / 5xx** → 自动切第二
- **400 / 422** → 不切换，直接返回
- 全部失败 → 返回明确错误 + 请求 ID

所有故障都由**模拟上游（mock）**制造，可控、可重复。

---

## 1. mock 使用速查

```bash
# 启动（默认 127.0.0.1:8100）
python mock_upstream.py          # 或双击 run_mock.bat

# 切换场景
curl -X PUT http://127.0.0.1:8100/_mock/scenario \
  -H "Content-Type: application/json" -d '{"scenario":"500"}'

# 查看当前场景 + 请求计数（用于验证"谁被访问了"）
curl http://127.0.0.1:8100/_mock/scenario
```

| 场景值 | 返回行为 | 用途 |
|---|---|---|
| `normal` | 200 + 标准 OpenAI JSON | 正常路径 |
| `timeout` | 延迟 **3 秒**再返回 | 触发超时切换 |
| `429` | HTTP 429 + Retry-After | 触发限流切换 |
| `500` | HTTP 500 | 触发 5xx 切换 |
| `400` | HTTP 400 | 验证"不切换" |

> ⚠️ **超时测试的配置前提（重要）**
> mock 的 timeout 延迟 3 秒。要让网关把它判定为"超时"，网关的**单上游超时时间必须小于 3 秒**（建议设 2 秒）。
> 如果网关超时 ≥ 3 秒，mock 延迟完已正常返回 200，就不会触发切换。

## 2. 推荐测试拓扑：双 mock 实例

为了能验证"第一正常时没有访问第二"，建议开**两个 mock 实例**，分别当分组的第一、第二成员：

```bash
# 实例 A（第一成员）
MOCK_PORT=8101 python mock_upstream.py

# 实例 B（第二成员）
MOCK_PORT=8102 python mock_upstream.py
```

分组配置（routeKey=`demo-route`，供调用测试）：

| 顺序 | displayName | baseUrl | 初始场景 |
|---|---|---|---|
| 1 | Mock-A | `http://127.0.0.1:8101/v1` | normal |
| 2 | Mock-B | `http://127.0.0.1:8102/v1` | normal |

两个实例**独立切场景、独立计数**。通过 `/_mock/scenario` 的 `requests` 计数，就能精确判断"第二上游到底被访问了没有"。

> 最终演示时把第二成员换成真实可用上游即可，清单逻辑不变。

## 3. 用例清单

### TC-01 正常路径

- **前置**：A=normal，B=normal
- **操作**：向网关发一次正常请求
- **预期**：HTTP 200，返回标准 OpenAI Chat Completion JSON
- **关键判据**：响应头 `X-Upstream: Mock-A`

### TC-02 正常时不访问第二

- **前置**：A=normal，B=normal
- **操作**：连发 3 次请求
- **预期**：3 次全部 200
- **关键判据**：**Mock-B 的请求计数 = 0**；Mock-A 计数 +3

### TC-03 超时切换

- **前置**：A=timeout，B=normal；网关单上游超时设为 2 秒（见 §1 提醒）
- **操作**：发一次请求
- **预期**：网关等待 A 超时后切到 B，最终返回 200
- **关键判据**：`X-Upstream: Mock-B`；Mock-A 计数 +1，Mock-B 计数 +1

### TC-04 429 切换

- **前置**：A=429，B=normal
- **操作**：发一次请求
- **预期**：切到 B，最终返回 200
- **关键判据**：`X-Upstream: Mock-B`

### TC-05 5xx 切换

- **前置**：A=500，B=normal
- **操作**：发一次请求
- **预期**：切到 B，最终返回 200
- **关键判据**：`X-Upstream: Mock-B`

### TC-06 全部失败

- **前置**：A=500，B=500
- **操作**：发一次请求
- **预期**：HTTP 502，返回 ErrorEnvelope 格式错误
- **关键判据**：`error.type = all_upstreams_failed`，响应头带 `X-Request-Id`

### TC-07 400 不切换

- **前置**：A=400，B=normal
- **操作**：发一次请求
- **预期**：HTTP 400 直接返回，**不访问 B**
- **关键判据**：**Mock-B 计数 = 0**；返回 400

### TC-08 故障恢复

- **前置**：先把 A 切 500 触发一次切换，再切回 A=normal
- **操作**：再次发请求
- **预期**：恢复走第一上游
- **关键判据**：`X-Upstream: Mock-A`

### TC-09 最大尝试次数与总超时

- **前置**：A=timeout，B=timeout（网关单上游超时 2 秒）
- **操作**：发一次请求
- **预期**：按最大尝试次数（3 次）尝试后停止，返回 502/504，**总耗时受控**（不应无限重试）
- **关键判据**：耗时 ≈ 单上游超时 × 最大尝试次数（如 2s×3=6s），含 `X-Request-Id`

### TC-10 请求头透传

- **前置**：A=normal
- **操作**：客户端带 `X-Request-Id: <自定义ID>` 发请求
- **预期**：响应头 `X-Request-Id` 与请求一致（网关生成或沿用）
- **关键判据**：响应头同时存在 `X-Request-Id` 与 `X-Upstream`

## 4. 自动化建议

每条用例都可以脚本化，固定套路是：

```
切换场景（控制接口） → 发请求（网关 /v1/chat/completions） → 断言（状态码 / 响应头 / 计数）
```

示例（TC-04，bash）：

```bash
# 1) 把 A 切到 429
curl -X PUT http://127.0.0.1:8101/_mock/scenario \
  -H "Content-Type: application/json" -d '{"scenario":"429"}'

# 2) 发请求（model 填分组 routeKey）
curl -i -X POST http://127.0.0.1:8787/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model":"demo-route","messages":[{"role":"user","content":"你好"}]}'

# 3) 断言：HTTP 200 且 X-Upstream: Mock-B
```
