# Personal Gateway Plus：开发路线图与协作拆分

> 状态：设计草案  
> 最后更新：2026-08-03  
> 关联文档：[产品与总体架构](README.md)｜[模块与自动路由设计](MODULES.md)

## 1. 开发原则

1. 先完成后端网关和接口契约，再接入 Web 与 Android，避免三端各自维护业务规则。
2. 先支持少量 OpenAI 兼容供应商，再通过适配器扩展非兼容平台。
3. 路由、计费和密钥管理均放在服务端；客户端只负责配置与展示。
4. 每个里程碑都必须具备自动化测试、可观测日志和明确验收标准。
5. 价格与活动信息必须标注来源、币种和更新时间，不能把过期数据当成实时价格。

## 2. 里程碑

### M0：工程骨架与接口契约

目标：建立可并行开发的基础，不急于实现完整业务。

任务：

- 建立 `server/`、`web/`、`contracts/` 和 `infra/` 目录。
- 确定后端技术栈、数据库和迁移工具。
- 在 `contracts/openapi.yaml` 定义供应商、模型、价格、活动、API 分组和网关接口。
- 设计统一错误码、分页、时间、金额和币种格式。
- 建立后端、Web 的格式化、静态检查、测试和 CI。

验收：

- 后端可启动并返回健康检查。
- OpenAPI 文件可通过校验并生成客户端类型。
- Android 和 Web 可以基于同一份契约构建。

### M1：单上游网关 MVP

目标：先打通一次真实、可审计的模型调用。

任务：

- 用户登录与基本权限校验。
- 供应商及上游端点的增删改查。
- API 密钥加密保存、脱敏展示与连通性测试。
- 实现 OpenAI Chat Completions 兼容入口。
- 记录请求 ID、上游、模型、耗时、Token 和错误摘要。

验收：

- 可添加一个上游并完成非流式和流式对话。
- 日志中不出现明文密钥或完整敏感请求体。
- 每次调用可以追踪到具体上游和结果。

### M2：API 分组与顺序故障切换

目标：实现项目最核心的“人工排序 + 自动路由”。

任务：

- API 分组和组成员管理。
- 拖拽排序、启用/停用和模型映射。
- 按顺序生成候选上游并执行故障切换。
- 实现错误分类、最大尝试次数、总超时和路由原因记录。
- 提供一次请求的完整路由尝试明细。

验收：

- 第一上游正常时不会访问后续上游。
- 第一上游发生可重试错误时按用户顺序切换。
- 参数错误、安全拒绝等不可重试错误不会盲目切换。
- 所有切换均能说明“为何切换、切到哪里、最终结果”。

### M3：健康检查、熔断与流式可靠性

目标：减少反复访问已知故障上游，明确流式请求边界。

任务：

- 被动健康统计与可选的主动探测。
- Closed、Open、Half-open 熔断状态机。
- 冷却时间、连续失败阈值和恢复探测。
- 客户端取消传播、首字节超时和流式错误处理。
- 上游限流响应与网关并发保护。

验收：

- 熔断期间自动跳过故障上游，冷却后可试探恢复。
- 流式输出首个有效内容后不再静默切换，避免拼接两个回答。
- 压力测试下不会出现无上限重试或请求堆积。

### M4：模型目录、价格与活动聚合

目标：让用户在一个界面比较模型成本与供应商优惠。

任务：

- 统一模型目录和供应商模型映射。
- 价格快照、计价单位、币种和有效时间管理。
- 活动的适用范围、折扣条件、起止时间和来源链接管理。
- 优先实现官方接口或后台维护，再评估合规抓取。
- 展示数据更新时间、历史价格和过期状态。

验收：

- 同一模型可比较多个供应商的输入、输出和其他计费项。
- 活动不会覆盖原始价格，且可以追溯来源。
- 数据过期或缺失时界面有明确提示。

### M5：用量、成本与管理后台

目标：形成可管理、可解释的个人网关控制台。

任务：

- 用量统计、成本估算和时间范围筛选。
- 供应商、模型、分组和上游维度的仪表盘。
- 路由记录、失败原因和健康状态界面。
- 预算预警、请求限额和审计日志。
- 数据导出与敏感记录保留策略。

验收：

- 用户可以定位一次失败调用及其每次路由尝试。
- 估算成本明确标注价格快照和币种。
- 权限、审计和数据清理策略经过测试。

### M6：Android 接入与生产加固

目标：让现有 Android 应用复用统一后端，并具备可部署能力。

任务：

- Android 改为读取服务端模型、价格、活动和分组数据。
- 保留当前比价体验，增加网关状态和基础管理入口。
- Docker 化部署、备份恢复、配置检查和升级脚本。
- 完成安全测试、故障演练、性能基线和部署文档。

验收：

- Web 与 Android 展示的数据和路由结果一致。
- 重启和升级不丢失配置，备份可以恢复。
- 发布前安全清单、回滚方案和演示流程齐全。

## 3. 可并行工作流

| 工作流 | 主要负责范围 | 前置依赖 | 交付物 |
|---|---|---|---|
| 契约与架构 | OpenAPI、领域模型、错误码 | 无 | `contracts/`、架构决策记录 |
| 后端控制面 | 供应商、模型、价格、活动、分组 | M0 契约 | 管理 API、数据库迁移 |
| 网关数据面 | 代理、路由、熔断、流式传输 | M0 契约 | 网关 API、路由测试 |
| Web 前端 | 控制台、排序、价格及活动展示 | 可先使用 Mock | `web/`、端到端测试 |
| Android | 服务端接入与移动展示 | M1/M4 接口稳定 | `app/` 改造、UI 测试 |
| 基础设施 | CI、容器、监控、备份 | 工程骨架 | `infra/`、部署文档 |

协作时，控制面和数据面可以由不同开发者负责，但路由规则与错误码必须先写进契约和测试用例。

## 5. 测试策略

- 单元测试：候选排序、模型匹配、错误分类、金额计算、活动有效期和熔断状态机。
- 集成测试：使用模拟上游分别返回超时、401、429、5xx、无效流和正常响应。
- 契约测试：确保 Web、Android 与服务端生成类型保持一致。
- 端到端测试：创建分组、调整顺序、发起请求、模拟故障并查看路由记录。
- 安全测试：密钥泄漏、SSRF、越权、日志脱敏、恶意上游响应和请求体限制。
- 性能测试：并发代理、流式长连接、连接池、总超时和熔断恢复。

路由测试必须覆盖“没有开始输出时可切换”和“已经向用户输出后不可静默切换”两类情况。

## 6. 协作规范

### 分支与提交

- 每个任务使用独立分支，建议格式：`codex/pgp-编号-简短描述`。
- 提交保持单一目的，避免把格式化、重构和新功能混成一个提交。
- 数据库结构变化必须附迁移文件；接口变化必须同步 OpenAPI。

### Pull Request

PR 描述至少包含：

- 解决的问题和不在本次范围内的内容。
- 接口、数据库、配置或安全方面的影响。
- 测试方式和关键结果。
- UI 变化截图，或网关路由日志示例。
- 回滚方式及兼容性说明。

### 完成定义（Definition of Done）

一个任务只有在以下条件满足后才算完成：

- 实现和验收标准一致，无未说明的行为变化。
- 核心路径有自动化测试，且现有测试通过。
- 不记录明文密钥或敏感请求内容。
- 接口、配置和部署变化已更新文档。
- 错误可诊断，重要操作可审计。
- 代码通过格式化、静态检查和评审。

## 7. 开工前需要确认的决策

| 决策 | 第一版建议 |
|---|---|
| 用户模式 | 先做单用户自托管，数据模型预留 `user_id` |
| 后端位置 | 独立 `server/`，作为唯一业务与路由中心 |
| 数据库 | 开发可用 SQLite，正式环境优先 PostgreSQL |
| 密钥保护 | 主密钥来自环境变量或密钥服务，库内只存密文 |
| 首批供应商 | 先选 2～3 个 OpenAI 兼容平台验证适配层 |
| 首批协议 | Chat Completions 优先，随后评估 Responses 与 Embeddings |
| 价格来源 | 官方 API/官方页面 + 人工审核，保留来源和时间 |
| 币种处理 | 保存原始币种，展示层可按带时间戳的汇率换算 |
| 路由策略 | 先做固定优先级和熔断，暂不自动按最低价改序 |
| 预算行为 | 第一版只预警，不默认阻断用户请求 |

这些决策一旦改变，应新增架构决策记录（ADR），而不是只在聊天或提交信息中说明。

## 8. 推荐启动顺序

第一轮先完成 PGP-001～PGP-006，得到可工作的单上游网关；第二轮完成 PGP-101～PGP-104，交付核心自动路由；第三轮再并行推进价格活动聚合和 Web 控制台。这样每一阶段都有可演示成果，也能尽早验证最有风险的代理、密钥与流式切换逻辑。
